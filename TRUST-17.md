# TRUST-17: Proposal for *17 Community Norms for Trustworthy AI Agents in Science*

TRUST-17 is an initial proposal for defining community expectations for how scientific agents should behave, be engineered and evaluated, and be governed throughout their operational lifecycle.

These seventeen norms are applicable to all AI agents that materially participate in scientific work, not just enterprise agents. These norms should be applied proportionately based on risk, autonomy, and whether the agent is private, shared, or operational.

Two key points need to be made:

1. *These norms are universal “expectations”.*&nbsp;&nbsp;

These are not best practices, but provide the starting point to develop best practices which can vary within the scientific community.

2. *The evidence, rigor, and implementation required to satisfy alignment with these norms should be proportional to the agent's role and risk.*

A potential three-tier model would be:

| Agent context | Example | How norms apply |
| ----- | ----- | ----- |
| **Personal / exploratory** | Scientist's personal skill for literature search or exploratory analysis | Lightweight application; primarily Layer 1, with basic provenance and awareness of limitations |
| **Shared / research** | Lab-developed agent shared with collaborators or published with a paper | Layers 1 \+ 2 strongly apply; Layer 3 begins to apply because others depend on it |
| **Operational / institutional** | Agency/Organization repository agent, production science workflow, autonomous data-processing agent | All three layers apply, with formal specifications, evaluation evidence, monitoring, stewardship, change control |

# **Layer 1 — Agent-Level Norms**

## **These norms define how a scientific agent should behave?**

### **1\. Defined Purpose and Boundaries**

A scientific agent should have a clearly documented purpose and operating scope.

Users should be able to understand:

* what the agent is intended to do;  
* who it is intended to support;  
* the scientific domain or operating context in which it is intended to work;  
* the role it is expected to play in the scientific workflow;  
* what scientific tasks it can perform;  
* the types of outputs or actions it is expected to produce;  
* what assumptions it makes;  
* what resources and tools it is allowed to use;  
* any conditions or limitations on how its outputs should be used, including when independent review or verification is required; and  
* what it should not do.

An agent should recognize when a request falls outside its intended or evaluated capabilities.

**Norm: Scientific agents should operate within clearly defined and documented boundaries.**

&nbsp;

### **2\. Grounding in Appropriate and Authoritative Scientific Evidence**

Scientific agents should base factual claims and scientific conclusions on identifiable evidence appropriate to the scientific question and use case.

What constitutes appropriate or authoritative evidence may vary by scientific domain and use case and should be explicitly identified during agent design with appropriate domain expertise.

Relevant evidence may include:

* curated scientific data repositories;  
* peer-reviewed publications;  
* authoritative scientific databases and knowledge resources;  
* validated scientific models;  
* documented scientific software;  
* instrument, mission, or observational records; and  
* authoritative metadata and supporting documentation.

Agents should make it possible to distinguish evidence obtained from scientific sources from conclusions or interpretations generated by the agent.

Where scientific claims depend on external evidence, users should be able to identify the evidence supporting those claims.

**Norm: Scientific claims produced by agents should be grounded in appropriate, identifiable evidence and should be traceable to the evidence that supports them.**

### **3\. Controlled and Authorized Use of Tools, Data, and Services**

Scientific agents may interact with repositories, APIs, databases, software, models, instruments, workflows, or other agents.

Such interactions should occur within defined authority boundaries. These boundaries should govern both **what resources an agent may access and what actions it may perform through them**.

Depending on the use case, authority may specify:

* permitted data and services;  
* permitted tools or classes of tools;  
* allowed operations, such as read, compute, modify, or publish;  
* applicable permissions and access controls; and  
* conditions under which consequential actions require additional authorization or human approval.

An agent should not silently expand its access, exceed its granted permissions, or perform actions beyond its authorized role.

When an authorized tool or service fails or is unavailable, the agent should not silently substitute resources or actions outside its approved authority.

Technical mechanisms such as tool protocols, authorization systems, controlled interfaces, and agent-to-agent protocols can help implement these boundaries.

**Norm: Scientific agents should access data, tools, and services and perform actions only within explicitly defined and granted authority.**

&nbsp;

### **4\. Uncertainty, Limits, and Escalation**

Scientific agents should identify and communicate conditions that limit the reliability or supportability of their outputs, including:

* incomplete or missing evidence;  
* conflicting evidence;  
* ambiguous requests;  
* failed or unavailable resources;  
* results outside validated or evaluated conditions; and  
* requests outside the agent's intended capabilities or authority.

Agents should respond proportionately to these conditions. Depending on the situation, an agent may:

* request clarification;  
* explain the relevant limitation or conflicting evidence;  
* provide a clearly qualified or provisional result;  
* state that available evidence is insufficient to support a conclusion;  
* abstain from making a conclusion;  
* refuse an action outside its authority; or  
* escalate to an appropriate human reviewer.

Where uncertainty or limitations materially affect a scientific result, the agent should communicate the **basis for that limitation** rather than presenting unsupported conclusions with unwarranted confidence.

**Norm: Scientific agents should make material limitations and uncertainties apparent and should clarify, qualify, abstain, refuse, or escalate when a scientifically supportable response cannot otherwise be provided.**

### **5\. Traceability and Process Provenance**

Important scientific outputs should be traceable to the evidence, actions, and processes used to produce them.

Depending on the scientific and operational risk of the use case, this may include:

* evidence and datasets used, including relevant versions;  
* publications or knowledge resources consulted;  
* queries or retrieval operations performed;  
* tools, software, models, or other agents invoked;  
* significant inputs and outputs of those operations;  
* material transformations or computational steps;  
* agent and model versions;  
* important intermediate results;  
* human interventions or approvals; and  
* significant failures, exceptions, or substitutions that affected the result.

The goal is not to capture or expose every internal model reasoning step, but to preserve the externally meaningful evidence, actions, transformations, and decisions needed for a knowledgeable person to understand and assess how an important scientific output was produced.

**Norm: Scientific agent outputs should carry sufficient provenance of the evidence and processes used to produce them so that their scientific basis and processing can be independently assessed.**

# **Layer 2 — Development and Verification Norms**

## **What norms should govern the design, evaluation, and assurance of a scientific agent prior to deployment and throughout its lifecycle?**

### **6\. Define Intended Use, Excluded Use, and Expected Outcomes**

Scientific agent development should begin with a clear definition of the scientific problem and the conditions under which the agent is intended to be used.

Before implementation, developers and relevant scientific stakeholders should agree on:

* the scientific problem or objective being addressed;  
* intended users;  
* intended uses;  
* explicitly excluded uses;  
* expected agent behavior and outcomes;  
* important assumptions and operating conditions;  
* acceptable and unacceptable failures;  
* the required level of reproducibility or consistency of scientifically material results; and  
* where human judgment, review, or approval is required.

These expectations provide the basis for subsequent agent specifications, implementation decisions, and evaluation.

**Norm: Scientific agent development should begin with documented intended and excluded uses, expected behavior and outcomes, operating assumptions, and acceptable and unacceptable failure conditions.**

### **7\. Develop from Explicit and Reviewable Specifications**

The important scientific and behavioral characteristics of an agent should be explicitly specified rather than left to emerge solely from prompts, model behavior, or implementation choices.

The specification should translate the intended uses, expected behaviors, operating assumptions, and failure conditions defined for the agent into reviewable and, where possible, testable requirements.

Depending on the use case, specifications should address:

* scientific grounding resources and rules for selecting appropriate evidence;  
* allowed data sources and relevant source constraints;  
* tools, permissions, action authority, and applicable security boundaries;  
* expected workflow, decision, and interaction behavior;  
* uncertainty, fallback, stop, and escalation behavior;  
* required human decision, review, approval, or escalation points;  
* domain terminology, semantics, units, conventions, and scientific constraints where relevant;  
* provenance requirements, including what evidence, actions, versions, and interventions must be recorded; and  
* evaluation criteria and acceptance thresholds.

Specifications should be established before consequential agent behavior is relied upon and should evolve in a controlled manner as requirements and implementation change.

Structured engineering approaches can help translate these requirements into documented, reviewable, and testable agent specifications.

**Norm: The scientific behavior, authority, controls, provenance, and evaluation requirements of an agent should be explicitly specified so that its implementation can be reviewed and tested against intended behavior.**

### **8\. Include Appropriate Scientific and Domain Expertise in Design and Review**

Scientific validity cannot be established through technical testing alone.

People with appropriate scientific, data, repository, methodological, software, operational, or other relevant expertise should participate at appropriate points in the agent lifecycle. The expertise required and degree of involvement should reflect the scientific task and the consequences of error.

Expert participation may be particularly important when defining or reviewing:

* appropriate and authoritative scientific evidence;  
* domain terminology, semantics, units, conventions, and scientific constraints;  
* scientifically acceptable methods, interpretations, and decision criteria;  
* representative scientific use cases and evaluation scenarios;  
* reference answers or evaluation criteria where appropriate;  
* anticipated scientific failure modes;  
* acceptable and unacceptable scientific outcomes; and  
* scientific release or acceptance criteria.

Expert involvement should inform both the design of the agent and assessment of whether its behavior is scientifically appropriate for its intended use.

**Norm: Scientific agents should be designed and reviewed with appropriate scientific and domain expertise sufficient to establish their scientific validity for the intended use.**

### **9\. Evaluate Against Realistic Scientific Tasks and Failure Conditions**

Scientific agents should be evaluated using representative scientific tasks and operating conditions derived from their intended use.

Evaluation should test not only successful or typical cases, but also:

* difficult or ambiguous scientific tasks;  
* incomplete, missing, or conflicting evidence;  
* requests outside the agent's intended scope;  
* known and anticipated failure modes;  
* tool or resource failures;  
* inappropriate or unauthorized requests; and  
* conditions outside the agent's evaluated operating envelope.

Performance should be defined in terms appropriate to the scientific use case and may include:

* scientific correctness and completeness;  
* accuracy and appropriateness of supporting evidence, citations, and resources;  
* correct use of scientific tools and data;  
* adherence to specified workflow and authority boundaries;  
* appropriate handling of uncertainty and unsupported conclusions;  
* correct abstention, refusal, or escalation behavior;  
* completeness of required provenance; and  
* consistency of scientifically material results where required.

Evaluation should assess both **the quality of the scientific output and whether the agent produced it through acceptable evidence, tools, and processes**.

Benchmarks, evaluation scenarios, and acceptance thresholds should be defined before release and should reflect the scientific consequences of failure. Appropriate scientific and domain experts should inform those criteria.

Evaluation results should identify the material system configuration tested, including relevant agent, model, grounding resources, tools, and versions.

Where relevant, operational measures such as latency, cost, token use, or computational efficiency may also be evaluated, but they should not substitute for scientific validity.

**Norm: Scientific agents should demonstrate acceptable scientific and behavioral performance against realistic tasks, failure conditions, and predefined acceptance criteria before release.**

### **10\. Define Human Oversight and Decision Authority**

Human oversight should be deliberately designed into scientific agent workflows where scientific or operational risk requires it.

Developers should explicitly determine:

* when human consultation, review, approval, intervention, or override is required;  
* what decisions or actions remain under human authority;  
* what expertise or authority a human reviewer must possess;  
* what information, evidence, and provenance the reviewer needs to make an informed decision;  
* what conditions require the agent to stop or escalate rather than proceed independently;  
* what ability an authorized human has to stop, reject, override, or reverse an agent action where appropriate; and  
* how significant human approvals, interventions, or overrides are recorded.

The degree of human oversight should be proportionate to the scientific and operational consequences of the agent's actions.

Human involvement should provide meaningful decision authority rather than functioning only as nominal or passive review.

**Norm: Where scientific or operational risk requires human oversight, the points of human intervention, decision authority, escalation, and override should be explicitly defined as part of the agent system.**

### **11\. Version and Re-evaluate Material Changes**

Scientific agents can change when their components, dependencies, configurations, or important inputs change.

Material changes may include changes to:

* the underlying AI model;  
* prompts, instructions, or behavioral policies;  
* scientific context or grounding resources;  
* tools, APIs, or external services;  
* orchestration or workflow logic;  
* permissions or authority boundaries;  
* datasets, dataset versions, or other scientific inputs; and  
* evaluation or acceptance criteria.

Material system configurations should be versioned so that important scientific outputs and evaluation results can be associated with the agent configuration that produced them.

When a material change occurs, the agent should be re-evaluated against the relevant specifications, benchmarks, and acceptance criteria to determine whether scientific behavior, authority boundaries, provenance, or other important properties have changed.

The scope of regression testing and re-evaluation should be proportionate to the nature and consequences of the change.

Changes in external dependencies or scientific inputs may also require reassessment, even when the agent's own code has not changed.

**Norm: Material changes to a scientific agent or its important dependencies and inputs should be versioned and should trigger proportionate regression testing and re-evaluation against relevant scientific and behavioral requirements.**

# **Layer 3 — Operational and Ecosystem Norms**

## **What norms should be followed for sharing, operating, monitoring, maintaining and governing a scientific agent?**

### **12\. Assign Clear Stewardship and Accountability**

Operational scientific agents should have clearly identified scientific and technical stewardship.

The individuals, teams, or organizations responsible for an agent should be identifiable, and their responsibilities and authority should be clear.

Depending on the use case, responsibilities may include:

* maintaining scientific integrity;  
* technical and operational maintenance;  
* maintaining documentation and evaluation evidence;  
* responding to reported problems or incidents;  
* reviewing and approving material changes;  
* initiating re-evaluation when needed;  
* restricting or suspending operation when risks emerge; and  
* deciding when an agent should be deprecated or retired.

Accountability may be distributed across multiple roles, but responsibility for both **scientific integrity and technical/operational integrity** should be identifiable.

Responsible parties should have, or have a defined mechanism to exercise, the authority necessary to fulfill those responsibilities.

Current stewardship and support status should be transparent so that users can distinguish actively maintained agents from unsupported, deprecated, or retired ones.

**Norm: Operational scientific agents should have identifiable scientific and technical stewardship, with clearly defined responsibilities, authority, and support status throughout their operational life.**

### **13\. Publish Standardized Agent Documentation**

Scientific agents that are shared or made available for operational use should be accompanied by documentation sufficient for users to understand what the agent is, how it is intended to be used, what evidence supports its use, and what limitations or obligations apply.

Documentation should describe, as appropriate:

* intended and excluded uses;  
* scientific scope and operating conditions;  
* data, evidence, and knowledge sources;  
* significant tools, models, services, and dependencies;  
* important assumptions and scientific constraints;  
* evaluation evidence and the material agent configuration to which it applies;  
* known limitations and failure conditions;  
* required human oversight or review;  
* provenance and traceability capabilities;  
* applicable license and terms of use;  
* version history and material changes;  
* current lifecycle and support status;  
* creators and significant contributors;  
* responsible scientific and technical stewards or organizations; and  
* where to find additional technical, evaluation, or governance information.

Documentation should be maintained with material agent changes and should use structured, interoperable metadata where practical.

Community documentation templates and established FAIR, research-software, and metadata practices may provide useful implementation foundations.

**Norm: Scientific agents should be accompanied by maintained, standardized documentation sufficient for users to determine their intended use, scientific basis, evaluation status, limitations, provenance, stewardship, and current support status.**

### **14\. Preserve Attribution, Provenance, and Scientific Lineage**

Scientific agents should preserve appropriate attribution to the resources and contributors on which their outputs depend and maintain sufficient provenance to identify how those resources contributed to the result.

Relevant resources may include:

* datasets and repositories;  
* publications and knowledge resources;  
* scientific software and algorithms;  
* scientific models;  
* AI and foundation models;  
* other agents and services;  
* instruments or observational resources; and  
* human contributors where appropriate.

Where material to scientific interpretation or reproducibility, attribution and provenance should include persistent identifiers, versions, or other information needed to identify the specific resources used.

When agents create derived scientific products, provenance and lineage should remain connected to the original inputs and significant transformations used to produce them.

Where an agent materially contributes to a scientific output, the identity and relevant version of the agent should itself be part of the provenance record.

Attribution and provenance information should be preserved in forms appropriate to the scientific use case and, where practical, in structured and interoperable forms.

**Norm: Agent-mediated science should preserve appropriate attribution and sufficient provenance and lineage to identify the scientific resources, models, agents, transformations, and contributors that materially shaped an output.**

### **15\. Make Scientific Agents Discoverable, Versioned, and Citable**

Scientific agents that are shared or reused beyond their original development context should be treated as identifiable research and software-enabled scientific objects.

Where appropriate, agents should:

* be registered, published, or otherwise made discoverable through a trusted and persistent location;  
* have stable, identifiable versions or releases;  
* use persistent identifiers appropriate to the way they are shared, such as DOIs where suitable;  
* provide clear citation guidance that identifies the agent and relevant version used;  
* provide human-readable metadata describing the agent, version, stewardship, and current lifecycle status;  
* provide structured and interoperable metadata where practical; and  
* link to relevant documentation, evaluation evidence, version history, and other assurance information.

Discoverability mechanisms should enable users to distinguish among versions and determine whether an agent is active, supported, deprecated, unsupported, or retired.

**Norm: Reusable scientific agents should be persistently discoverable, version-identifiable, and citable, with sufficient metadata to connect users to their documentation, evaluation evidence, stewardship, and current status.**

### **16\. Monitor Supported Agents After Release**

Evaluation should continue after release for scientific agents that are represented as active or supported.

Monitoring should be appropriate to the scientific and operational risk of the use case and may include detection of:

* degradation in scientific or behavioral performance;  
* unsupported or poorly grounded scientific claims;  
* changes in data, models, tools, APIs, or other dependencies;  
* operation outside evaluated or intended conditions;  
* unexpected or unauthorized tool behavior;  
* failures of uncertainty, abstention, or escalation behavior;  
* user-reported errors, repeated corrections, or recurring feedback signals; and  
* newly observed or emerging failure modes.

Monitoring should address not only technical operation but also scientifically meaningful behavior where appropriate.

Material monitoring findings should trigger proportionate review, re-evaluation, mitigation, restriction, suspension, or other lifecycle actions.

Monitoring obligations should be consistent with the agent's declared lifecycle and support status. Agents that are no longer actively monitored or maintained should be clearly identified as unsupported, deprecated, archived, or retired rather than continuing to appear as actively supported systems.

**Norm: Scientific agents represented as active or supported should be monitored after release for meaningful scientific, behavioral, and operational degradation, with monitoring obligations and response processes appropriate to their risk and declared support status.**

### **17\. Govern Changes, Contributions, Deprecation, and Retirement**

Scientific agents that are shared, operational, or community-maintained should have transparent processes for governing material changes and lifecycle transitions.

These processes should address, as appropriate:

* proposing and reviewing changes;  
* accepting and reviewing external contributions;  
* modifying scientific grounding, data sources, models, tools, or behavioral policies;  
* changing permissions or action authority;  
* determining the level of scientific and technical review required for a change;  
* approving new releases or versions;  
* recording material changes and contributor roles;  
* restricting or suspending an agent when significant risks emerge;  
* deprecating outdated or unsupported versions; and  
* retiring agents that can no longer be responsibly supported.

The rigor of review and approval should be proportionate to the scientific and operational consequences of the change.

Roles and decision authority for approving changes, releases, deprecation, suspension, and retirement should be clearly defined.

Deprecated or retired agents should have their lifecycle status clearly indicated. Where appropriate, historical versions, documentation, provenance, and persistent identifiers should remain available so that prior scientific uses can still be understood and cited.

**Norm: Material changes, external contributions, releases, deprecation, suspension, and retirement of shared scientific agents should follow transparent, proportionate governance with clearly defined decision authority and preserved lifecycle records.**
